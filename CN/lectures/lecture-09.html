Transport Layer Principles & Multiplexing / Demultiplexing

1.1 Process-to-Process Logical Communication

The Transport Layer provides logical communication between application processes running on different network hosts. While the Network Layer delivers packets between host IP addresses (host-to-host), the Transport Layer extends this to process-to-process delivery.

1.2 Transport Layer vs. Network Layer Responsibilities

An analogy: Host IP addresses are like physical apartment building addresses; Port numbers are like individual mailbox numbers or apartment occupant names within a building.

1.3 Multiplexing & Demultiplexing Mechanics

  • Multiplexing (Sender): Gathering data chunks from multiple application sockets, encapsulating them with transport headers (ports), and passing segment packages to the Network Layer.
  • Demultiplexing (Receiver): Inspecting transport header fields of incoming segments to direct data to the correct target application socket.
2

Connectionless Transport: User Datagram Protocol (UDP)

2.1 Philosophy & RFC 768 Specification

UDP (User Datagram Protocol, RFC 768) is a minimal, connectionless transport protocol. It provides direct access to the underlying IP layer with only two added services: port-based demultiplexing and lightweight error checking (checksum).

2.2 Lightweight Bare-Bones Transport

UDP does not establish connections (no handshake delays), does not maintain connection state at endpoints, does not control congestion, and does not guarantee packet arrival order or delivery.

2.3 Advantages of UDP over TCP

Why Developers Choose UDP
  • Fine-Grained Application Control: Application decides exactly what data to send and when (no delays caused by TCP congestion throttling).
  • Zero Connection Setup Overhead: Eliminates the 1 RTT (Round Trip Time) 3-way handshake delay.
  • No Connection State: Server memory requirements are minimal (no buffers, sequence parameters, or timers).
  • Small Header Overhead: UDP header is only 8 bytes long, compared to 20+ bytes for TCP.

UDP Header Architecture & Checksum Computation

3.1 8-Byte UDP Header Field Structure

The UDP header consists of exactly four 16-bit (2-byte) fields totaling 8 bytes:

$$\text{UDP Header Size} = 8 \text{ Bytes}$$
UDP Header Anatomy
Bits 0–15 Bits 16–31
Source Port (16 bits)Destination Port (16 bits)
Length (16 bits, Header + Data)Checksum (16 bits)

3.2 Pseudo-Header Construction

To compute the UDP checksum, the sender prepends a 12-byte Pseudo-Header (containing Source IP, Destination IP, Protocol ID=17, and UDP Length) to the UDP segment. This ensures that IP routing errors are caught by transport validation.

3.3 One's Complement Summation Algorithm

The sender treats all 16-bit words in the pseudo-header, UDP header, and payload as integers, sums them using 1's complement arithmetic (carrying overflow bits back into the sum), and takes the bitwise NOT of the result.

UDP Use Cases & Application Suitability

4.1 Domain Name System (DNS)

DNS queries use UDP port 53. Request/response exchanges fit inside a single datagram. Avoiding TCP handshake overhead speeds up domain lookup latency globally.

4.2 Real-Time Streaming & Multimedia (RTP, VoIP)

In live audio/video calls (VoIP, Zoom, WebRTC), losing a frame is preferable to delaying subsequent audio frames waiting for retransmission. Low latency is prioritized over 100% reliability.

4.3 HTTP/3 & QUIC Protocol Evolution

Modern web protocol HTTP/3 replaces TCP with QUIC, a user-space reliable protocol built on top of UDP. QUIC eliminates Head-of-Line (HoL) blocking and accelerates TLS handshakes.
