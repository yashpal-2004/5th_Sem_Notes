Electronic Mail Architecture & Core Components

1.1 User Agents & Mail Servers

Electronic mail (email) is a high-level distributed application consisting of three main structural components: User Agents (UAs), Mail Servers, and the Simple Mail Transfer Protocol (SMTP).

  • User Agent (UA): Software allowing users to read, compose, reply to, forward, and organize messages (e.g., Outlook, Apple Mail, Thunderbird, Webmail interfaces like Gmail).
  • Mail Server: The core infrastructure hosting user mailboxes, managing outgoing/incoming message queues, and executing background routing protocols.

1.2 Spooling & Message Queue System

When a user sends a message, it does not travel directly to the recipient's personal device. Instead, the sender's User Agent pushes the email to their local mail server's outgoing message queue (spool).

If the recipient's mail server is temporarily unreachable or offline, the sender's server holds the message in its queue and retries transmission periodically (typically every 15–30 minutes for up to several days) before generating a non-delivery report (bounce email).

1.3 Asynchronous Email Delivery

Email delivery operates asynchronously. The sender and recipient do not need to be online simultaneously. Communication happens in two distinct stages: (1) Push via SMTP from sender UA to sender mail server, and across mail servers; (2) Pull via POP3/IMAP/HTTP from recipient mail server to recipient UA.

2

Simple Mail Transfer Protocol (SMTP)

2.1 SMTP Mechanics & Push Protocol Paradigm

SMTP (Simple Mail Transfer Protocol) is a legacy client-server protocol (RFC 5321) used to transfer mail messages reliably across TCP connections. SMTP is strictly a push protocol: the client initiating the TCP connection is always the party pushing a message.

2.2 TCP Port 25 & Handshake Commands

SMTP operates over TCP port 25 (standard server-to-server relay) or port 587 (authenticated client-to-server submission). The session consists of plain ASCII text commands sent by the client and 3-digit status codes returned by the server.

Core SMTP Command Sequence
  • HELO / EHLO: Client identifies itself to the SMTP server.
  • MAIL FROM: <sender@domain.com>: Identifies the message originator.
  • RCPT TO: <recipient@domain.com>: Identifies the target mailbox recipient.
  • DATA: Signals the start of the message body (terminated by a single dot . on its own line).
  • QUIT: Terminates the SMTP session.

2.3 In-Band Command Execution & Response Codes

SMTP commands and message payload share the exact same TCP stream (in-band transmission). Server responses begin with 3-digit numerical codes followed by explanatory text:

  • 220: Service Ready
  • 250: Requested mail action okay / completed
  • 354: Start mail input; end with <CR><LF>.<CR><LF>
  • 550: Requested action not taken (e.g., mailbox unavailable)

Mail Access Protocols: POP3 vs. IMAP

3.1 The Need for Pull Protocols

SMTP cannot be used to deliver emails directly to a recipient's user agent because end-user devices are frequently turned off, mobile, or behind NAT firewalls. Therefore, recipient mail servers hold incoming messages in mailboxes until the user agent uses a pull protocol to fetch them.

3.2 POP3 (Post Office Protocol v3)

POP3 (RFC 1939) operates on TCP port 110 (or 995 over TLS). It follows an extremely simple 3-phase workflow: Authorization, Transaction, and Update.

  • Download-and-Delete Mode: Messages are downloaded to the client device and permanently deleted from the mail server.
  • Download-and-Keep Mode: Messages are retained on the server, but client states (e.g., read/unread status) are localized to one device.
  • Limitation: Does not support server-side folder creation or multi-device synchronization.

3.3 IMAP (Internet Message Access Protocol)

IMAP (RFC 3501) operates on TCP port 143 (or 993 over TLS). Unlike POP3, IMAP maintains state across multiple devices by storing all messages, folders, and flag metadata directly on the central mail server.

MIME Extension & Binary Content Encoding

4.1 ASCII Limitation of Legacy SMTP

Original SMTP was restricted to 7-bit ASCII text formatting. Non-ASCII characters (Unicode, foreign alphabets) and binary attachments (images, audio, PDF files, executables) could not be transmitted natively over 7-bit ASCII SMTP streams.

4.2 MIME Headers (RFC 2045)

MIME (Multipurpose Internet Mail Extensions) extends the structure of email headers to declare arbitrary content types and encoding methods without modifying underlying SMTP protocol rules.

Key MIME Header Lines
  • MIME-Version: 1.0
  • Content-Type: multipart/mixed; boundary="----=_NextPart"
  • Content-Transfer-Encoding: base64

4.3 Base64 & Quoted-Printable Encoding Algorithms

Binary attachments are encoded into 7-bit ASCII strings prior to SMTP transmission:

  • Base64 Encoding: Groups binary data into 3-byte blocks (24 bits), splits them into four 6-bit integers, and maps each 6-bit integer (0–63) to printable ASCII characters [A-Z, a-z, 0-9, +, /]. Introduces a fixed 33% size expansion overhead.
  • Quoted-Printable: Used for mostly-text content containing occasional non-ASCII bytes. Replaces non-ASCII bytes with an equals sign followed by two hexadecimal digits (e.g., =E2=82=AC for €).

Email Infrastructure & Security Alignment

5.1 DNS MX (Mail Exchanger) Records

When a mail server needs to send an email to user@example.com, it performs a DNS query requesting the MX (Mail Exchanger) record for example.com. The DNS response returns the domain name and priority preference of the destination mail server.

5.2 Email Spoofing & Security Vulnerabilities

Because SMTP MAIL FROM and header From: fields are plain ASCII strings supplied by the client, malicious actors can easily forge sender addresses (Email Spoofing) to execute phishing attacks.

5.3 Authentication Frameworks: SPF, DKIM & DMARC

Email Anti-Spoofing Triad
  • SPF (Sender Policy Framework): Domain owners publish a DNS TXT record listing all IP addresses authorized to send mail on behalf of their domain.
  • DKIM (DomainKeys Identified Mail): Outgoing mail servers append a cryptographic digital signature (RSA/Ed25519) to header lines. Receiving servers verify the signature using the domain's public key published in DNS.
  • DMARC: Combines SPF and DKIM validation checks, allowing domain owners to specify policy rules (none, quarantine, reject) for handling unauthenticated emails.
